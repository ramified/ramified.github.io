# 如何更精确地描述 Math Workspace 需求

## 先说明：反复修改不完全是你的提示词问题

这次开发中出现的大量反复，并不能简单归因于“用户没有说清楚”。实现者本来就有责任先阅读原始计算器、调查依赖、识别已有行为，并在架构含义不清楚时先确认，而不是立即写代码。

不过，这类跨视图、跨会话、跨数据模型的功能非常复杂。如果提示词只描述“看起来像什么”，模型很容易自行补全“内部应该怎样工作”，而这些推断往往与你真正想要的状态关系不同。更精确的提示词能够明显减少这种试错。

最有效的方法不是写得特别长，而是把以下五件事说清楚：

```text
当前状态 + 用户操作 + 数据如何变化 + 屏幕如何变化 + 什么绝对不能变化
```

## 一、不要只描述相似物，要描述差异

“像 Windows File Explorer”很有帮助，但它不能唯一决定所有行为。例如：

- Ctrl/Shift 选择是否以当前排序后的顺序为准？
- 右键未选中的项目是否替换已有多选？
- 拖动是框选、移动、复制，还是建立数学关系？
- 关闭标签页是否删除其中的数据？
- 同名对象是否允许存在？

建议采用下面的表达方式：

> Assets 的选择规则以 Windows File Explorer 为参照，但只采用以下行为：单击替换选择，Ctrl 切换单项，Shift 按当前可见排序连续选择，Ctrl+Shift 扩展连续选择，空白处拖动为框选。项目拖动不表示移动文件；除明确指定的目标外，不建立跨视图关系。

这样，“参照物”提供直觉，“差异列表”消除推断空间。

## 二、用状态转换描述每个关键交互

对复杂操作，最好固定写六项：

1. **初始状态**：操作之前有哪些视图、对象和选中项？
2. **用户操作**：准确点击、拖动或输入什么？
3. **数据变化**：哪个模型中的哪些数据应该改变？
4. **屏幕结果**：用户应该立即看到什么？
5. **不变项**：哪些视图、卡片或字段必须保持原样？
6. **生命周期**：关闭、重开、刷新页面后是否保留？

例如，“Collect”如果只写成“收集相关对象”，至少有三种合理解释：

- 把 Sheaf Complex 画布对象保存到 Assets；
- 把 Assets 对象显示到 Sheaf Complex 画布；
- 只显示当前对象的依赖闭包。

更精确的写法是：

```text
初始状态：Assets 中有 X、Y、E，Sheaf Complexes 画布为空。
用户操作：在 Sheaf Complexes 画布工具栏点击 Collect。
数据变化：Assets 集合不发生任何变化；该 Sheaf Complexes 会话记录
          X、Y、E 为已投影对象。
屏幕结果：当前 Sheaf Complexes 画布立即显示 X、Y、E 及已有关系线。
不变项：不要切换到 Assets 视图，不要创建新 Asset，不要打开新的画布标签。
生命周期：关闭并重新打开此 Sheaf Complexes 标签后仍显示；刷新页面后清空。
```

这类描述通常比一句抽象的功能说明更省时间。

## 三、明确“谁拥有状态”

本项目最容易混淆的是：屏幕上看起来相邻的内容，实际不一定属于同一个会话。

建议在提示词中明确以下所有权：

| 内容 | 建议说明 |
| --- | --- |
| Asset 对象 | 属于唯一的 Assets 会话，页面刷新前有效 |
| 计算器画布 | 每个计算器会话独立保存 |
| Inspector 卡片 | 可以来自多个计算器，并同时显示 |
| 卡片顺序/折叠/隐藏 | 属于对应卡片会话，不随画布切换重置 |
| 画布高度 | 属于单个画布会话 |
| Sheaf Complex 中显示哪些 Assets | 属于该 Sheaf Complex 会话，不属于全局 |
| 数学名称 | 保存原始 LaTeX；普通文本只用于排序和无障碍 |

可以直接写：

> 请先给出一张 state ownership 表，再开始实现。每个状态只能有一个权威来源；其他地方只能读取或通过明确的投影/命令修改它。

这会迫使实现者在写事件监听器之前解决架构问题。

## 四、区分“视图”“会话”“卡片”和“当前来源”

不要把这些词互换使用：

- **View / 画布视图**：中间主区域中的一个标签页内容。
- **Session / 会话**：即使画布关闭，也可能继续存在的数学状态。
- **Card / 卡片**：Inspector 中的一块工具或结果 UI。
- **Card source / 卡片来源**：卡片属于哪个计算器会话或 Assets。
- **Picker source / 选择器来源**：Add card 菜单当前正在列出哪个来源的卡片。
- **Focus / 焦点**：当前接收键盘或画布操作的对象，不等于唯一可见来源。

例如，不要只写：

> Checking one switches the Inspector to that calculator.

如果你的真正意图是混合卡片，应写：

> Add card 菜单中的来源选择器只改变“菜单中列出的候选卡片”，不隐藏 Inspector 中已经显示的其他来源卡片。勾选一个卡片只显示该卡片；取消勾选只隐藏该卡片。任何时候都允许 Assets、Sheaf Complexes 和其他计算器的卡片同时存在。

## 五、数学字段要同时说明合法性和联动规则

只说“增加一个 selectbox”通常不够。数学对象引用需要说明：

- 允许引用的对象类型；
- 是否允许引用自己；
- 是否允许两个槽选择同一对象；
- 是否允许形成传递循环；
- 引用删除后如何处理；
- 选择后哪些派生字段立即更新；
- 修改是草稿还是立即保存；
- 保存时是否再次验证。

例如产品簇字段可以写成：

```text
first 和 second 只接受 variety。
正在编辑的产品簇本身不能作为任何因子。
允许 first 与 second 指向同一个普通 variety。
任何会形成直接或传递依赖循环的候选项都不出现在 picker 中，拖入时也拒绝。
选择因子后立即更新草稿 dimension，但直到点击 Save 才修改 Assets 模型。
Save 必须再次使用与 picker 完全相同的规则验证，防止候选项已被删除。
```

这种写法可以避免“UI 看起来对，但保存失败”或“一个字段变化清空另一个字段”。

## 六、明确区分原始 LaTeX、普通名称和视觉结果

对于数学名称，最好直接规定三种形式：

```text
rawName:  \mathcal{E}_{2}     // 编辑和保存
plainName: E_2                 // 排序、搜索、aria-label、MathJax 失败时回退
rendered: MathJax(rawName)     // 屏幕显示
```

并补充一句：

> 任何桥接、导入、投影或重新渲染都不得用 plainName 覆盖 rawName。

如果视觉形式非常重要，可以写出验收结果：

> 名称输入框中保存的是 `\mathcal{E}_{2}`；Assets 项目和 Sheaf Complexes 画布都应显示花体 E 和下标 2；DOM/模型中仍保留原始 LaTeX，而不是只保存 `E_2`。

## 七、把“不允许修改的范围”写在前面

对于历史计算器，建议在每次相关请求开头重复：

```text
边界：不得修改任何 standalone calculator 的 HTML/JS/CSS，不得让它们加载
workspace 脚本，也不得让 workspace 在运行时加载 standalone 页面。可以读取它们
作为行为规范。所有新逻辑必须位于 workspace-owned source 或独立 adapter 中。
```

“不要影响旧页面”仍可能被理解为“可以修改，只要测试看起来没变化”；上面的表达把文件边界、运行时依赖和允许的参考方式都说清楚了。

## 八、要求先做基线调查，再提交实现方案

当功能涉及旧计算器时，可以要求两阶段执行：

### 第一阶段：只调查，不编辑

要求输出：

- 原始实现涉及的文件和函数；
- 已有 UI 行为和隐藏联动；
- workspace 当前实现与原始实现的差异；
- 状态所有权图；
- 风险和需要浏览器验证的场景。

### 第二阶段：经确认后实现

这样可以在代码规模扩大之前发现“原始功能已存在”“术语理解错误”或“架构方向不对”。

如果你希望模型直接实现，也可以写：

> 先完成上述调查并在 commentary 中汇报关键发现；如果发现当前方案与原始行为冲突，先调整方案，再继续实现，不要机械执行旧假设。

## 九、给出验收矩阵，而不是只列功能

一个很实用的表格是：

| 场景 | 初始状态 | 操作 | 预期结果 | 不应发生 |
| --- | --- | --- | --- | --- |
| 修改 sheaf base | X、Y、E 已存在，E 在 Y 上 | 把 Base 拖到 X，Save | E 保存为 base=X，画布把 E 移到 X 附近并更新关系线 | Y 不删除，其他位置不重置 |
| 修改 map domain | domain=X，codomain=Y | domain 改为 Z | codomain 仍为 Y | codomain 不得变空 |
| 混合卡片 | 已显示 Assets Input 和 Matrix Result | 在 Sheaf 来源勾选 Hodge | 三种来源卡片同时显示 | 不得隐藏前两个卡片或打开画布 |
| 关闭画布 | Sheaf 画布和其卡片都有状态 | 关闭后重新打开画布 | 使用同一会话和原状态 | 不得新建默认对象 |

矩阵尤其适合发现组合错误。单独测试“能改 domain”和“能改 codomain”并不能保证改一个时另一个不会丢失。

## 十、截图和 DOM 信息怎样提供最有效

如果问题是视觉布局，最好同时提供：

- 一张“当前错误”的截图；
- 一张“正确参考”的截图；
- 浏览器宽度或设备尺寸；
- 指出需要比较的边界、间距、滚动条或层级；
- 如果知道的话，给出相关 class，但不要只给 class 名而不说明视觉目标。

例如：

> 在 1440×900 下，`.workspace-native-calculator` 的可见底边应与 `.canvas-panel.workspace-view-card` 的内容底边重合，允许 0–1px 取整误差；页面和该容器都不应出现纵向滚动条。只允许计算器内部结果区在内容溢出时滚动。

这比“高度看起来不对”更容易一次修准。

## 针对本项目的一条简化写法

以后如果不想写完整模板，至少可以用下面这段开头：

> 在修改前，请先把我的需求写成“初始状态 → 用户操作 → 权威数据变化 → 可见结果 → 必须保持不变”的状态转换，并检查原始 standalone calculator 中是否已经有对应逻辑。请明确 canvas、session、Inspector card、picker source 和 active object 的所有权。不要修改历史计算器；不要用结构性 source-string 测试代替真实浏览器交互测试。如果一个词有两种合理解释，先指出并根据我给的例子确定含义。

这段话不能替代具体需求，但可以显著降低实现者直接猜测架构的概率。

## 最后建议

复杂功能最省时间的方式通常不是一次写出巨大的完整计划，而是：

1. 先固定架构词汇和状态所有权；
2. 选择一个最小但完整的对象流程作为样板；
3. 在浏览器中验收这个流程；
4. 再扩展到其他类型和计算器；
5. 每次扩展都复用同一规则和测试矩阵。

这样做看似多了一个设计步骤，实际上会减少后面大量“这个字段为什么清空”“为什么卡片被隐藏”“为什么旧计算器变化了”之类的往返修复。
