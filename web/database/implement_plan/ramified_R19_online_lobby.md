# R19：联网大厅与房间流程设计

更新日期：2026-10-11。工作分支：`ramified_menu`。

**状态：设计草案，未实现。** 用户本轮明确要求先写设计文档。本稿只修改 Markdown；没有改动玩家页面、联网服务、翻译、存档或部署配置。下文分别标明用户要求、代码现状、建议与待确认项，建议不能当作已确认需求实施。

## 1. 用户已明确的目标

1. 有一个显示在线玩家和房间的界面。
2. 每个房间显示房间内玩家及游戏类型。
3. 创建房间时，房主先从游戏列表选择游戏并初始化；列表不包含推箱子这样的单人游戏。
4. 房主退出后，自动由第二位玩家接任房主。
5. 超过一定时间无人游戏的房间自动删除。

房主退出时如何处理他的棋手位置、“无人游戏”的判断与时长、在线玩家的统计范围仍需确认，不能仅凭这五条推定全部规则。

## 3. 先分清四种事情

这是本次设计的核心，页面只是这些规则的呈现。

| 概念 | 负责什么 | 例子 |
| --- | --- | --- |
| 大厅 | 发现在线玩家和可进入的房间 | 能看到某个五子棋房间正在等人 |
| 房间 | 聚集一组成员，保存房间配置和当前棋局 | 一局结束后仍可在同一房间继续 |
| 房主 | 管理这间房，不自动拥有其他人的落子权 | 白方接任房主后仍然是白方 |
| 棋手位置／阵营 | 决定谁能操作哪一方 | 原黑方退出，黑方会缺人；把房主交给白方不能补上黑方 |

因此，“房主移交”“棋手退出”“房间删除”是三个不同事件，分别处理。昵称只是显示名，不用于判断谁有房主权限或属于哪个阵营。

## 4. 页面和进入路径（建议，待确认）

建议在主菜单增加独立的“在线游戏 / Online play”入口，直接进入大厅。联网无需先选择本地存档；原“开始游戏 → 选择存档”的本地流程保持原样。

```text
主菜单
  开始游戏 → 选择存档 → 本地游戏列表 → 原准备页／选关
  在线游戏 → 联网大厅
               ├─ 创建房间 → 多人游戏列表 → 联网准备页 → 创建 → 房间等待页
               └─ 选择已有房间／输入房间码 → 加入 → 房间等待页或当前棋局
  设置

房间等待页 → 满足开局条件 → 当前对局 → 结束／再来一局
退出房间 → 联网大厅 → 主菜单
```

本稿将用户所说的“窗口”理解为**游戏框内的完整大厅页面**，沿用固定 4:3 外框、黑底白字标题、全屏和内部滚动，不添加居中小弹窗或新的卡片风格。具体入口位置仍列为待确认项，不借此重排 R18 的所有设置按钮。

### 大厅只展示必要信息

| 区域 | 内容 | 行为 |
| --- | --- | --- |
| 自己 | 沿用现有昵称设置 | 不额外增加注册流程 |
| 在线玩家 | 范围确认后的昵称和人数 | 显示事实，不把访问统计当作在线名单 |
| 房间列表 | 房间码、游戏类型、房间成员、房主标记、参赛人数／席位及等待／进行中等状态 | 加入资格由实际房间再次检查，列表可能短暂过期 |
| 操作 | 创建房间、原房间码加入、返回 | 保留房间码作为直接进入的办法 |

建议房间按行展示，成员昵称在同一行的附属文字中，不为每个玩家加一张卡片。多人列表过长可在内容区域滚动；全屏内容居中，窄屏区域上下排列。布局尺寸在之后的实现中检查，本轮不生成新的美术草图。

空列表、正在连接、获取失败必须是不同状态。获取失败不能显示成“当前没有玩家／房间”；保留重试和返回。

### 返回和退出不能混为一谈

- 建房游戏列表返回大厅；准备页返回该列表，“更多”返回准备页并保留本次修改。
- 按下最终创建之前不产生服务器房间；取消不会留下空房间。
- 房间内打开设置、返回棋盘，不表示离开房间，也不移交房主。
- 建议“退出房间”是明确操作，成功后返回大厅。房间未退出时不允许悄悄加入第二个房间。
- 刷新、关闭标签页、网络中断按断线处理，不能假定浏览器一定能送达主动退出消息。

## 5. 创建房间与游戏范围

### 保留现有支持范围

| 游戏 | 建房列表 | 联网准备要求 |
| --- | --- | --- |
| Hex | 包含 | 沿用现有棋盘和交换规则选项，两个阵营由联网玩家控制 |
| 五子棋 | 包含 | 沿用现有棋盘准备布局，移除本地 AI 控制者选项 |
| 围棋 | 包含 | 沿用棋盘、贴目等原选项 |
| 四子棋 | 包含 | 沿用棋盘与下落方向，不带入本地 AI |
| 黑白棋 | 包含 | 沿用棋盘选项 |
| 中国跳棋 | 包含 | 可用阵营随棋盘确定；同一人是否仍可控制多个阵营需确认 |
| 国际象棋 | 仅对局 | 按目录 `fideChessVariant` 过滤；不显示皇后等单人谜题 |
| 台球 | 仅双人模式 | 保留棋盘和原摆球流程，建房使用已确认的初始摆球 |
| 推箱子、2048、连连看 | 不包含 | 本轮不扩展其玩法或加入联机支持 |

复用原 2×3 游戏图片分页，按现有游戏顺序过滤，避免另维护一份图片或排序。国际象棋对局／谜题、台球单人／双人须按实际模式判断，不能只按游戏名称过滤；前端与服务端都要检查。

### 建房准备的建议规则

1. 新进入准备页使用现有玩家入口的棋盘／参数默认值；联网覆盖仅包括关闭本地 AI、台球固定双人、国际象棋固定对局。
2. 保留预览两侧切换、预览下方必要选项、左下更多、右下提交按钮；最终按钮为“创建房间”，不先偷偷开始一局本地游戏。
3. 两人游戏的“人类／AI”区域改为联网席位信息。建议创建者可选自己的阵营，其余空位显示等待玩家；默认第一阵营，其他加入者选择空位。跳棋的多阵营分配单独确认。
4. 本次准备内切换棋盘／更多再返回仍保留草稿。随机棋盘、拓扑和台球摆球只在准备中确定，创建时使用相同结果，不重新生成。
5. 创建后进入等待页，不立即允许落子。服务器保存唯一的初始棋局，其他成员加入时获取同一版本。
6. 创建请求成功但应答丢失时，重试应找到同一次创建的房间，避免连续生成重复房间；只完成创建、未成功连接的房间由空房间规则清理。

“创建后是否允许房主在原房间改棋盘／换游戏”尚未决定。建议首版创建后固定游戏和配置；若需要房间内修改，应另定义成员准备失效和棋局替换确认，不能默认覆盖已经开始的局。

## 6. 等待、开局与成员离席

### 等待页与开局（建议）

等待页显示游戏／棋盘名称、成员、阵营、房主和准备状态。参与者自行准备或取消准备；观战者没有落子权，也不阻碍参赛者完成准备。

首版建议保留现有“参与者均准备后开局”的方式，同时补齐两个条件：

- 双人游戏必须有两位不同的在线玩家，所需双方均有人控制。
- 跳棋至少两位不同的在线玩家，启用的全部阵营均有控制者；一人多阵营是否保留仍待确认。

若希望“所有人准备后，再由房主点击开始”，需明确选择该方案；不能同时把自动开局和房主手动开局写成要求。游戏开始后保留原棋盘和操作，不把房间成员列表一直盖在棋盘上。

### 房主移交（用户要求已确认，边界建议待确认）

主动退出后的自动移交已明确。建议将“第二位”定义为**剩余在线参赛成员中，最早成功加入房间的人**，不按棋子颜色、昵称排序或各客户端画面顺序判断。建议在宽限内断线重连保留原加入顺序；主动离开后再进房间算新加入。

| 场景 | 建议处理 |
| --- | --- |
| 房主明确退出房间 | 立即选出继任者并通知全体；保留房间码和当前棋局 |
| 同时有多人离开 | 服务端完成成员变更后选择一次有效继任者，不能出现两个房主 |
| 只是短时断线／刷新 | 建议保留 60 秒重连机会；到期仍未连接才移交。60 秒为建议值，不是用户已确认值 |
| 旧房主在移交后重连 | 作为普通成员返回，不自动夺回房主；原席位是否保留按断线／接替规则处理 |
| 新房主继续退出 | 按相同加入顺序继续移交 |
| 只剩观战者 | 观战者是否可以接任待确认；不能默默把观战者变成某一方棋手 |
| 无任何成员 | 暂无房主，进入空房间宽限；若允许在期限内重新加入，建议首位有效参赛者接任 |

移交由服务器决定并保存，不依靠房主浏览器先发出“指定继任者”的消息。因此关闭浏览器也有可执行的后续流程。转移的是管理权，不修改棋盘、轮到谁、阵营归属或已完成操作。

### 棋手离席（待用户选择）

这里对普通棋手和房主使用同一条规则，房主另外发生管理权移交。

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| A：保留棋局，等人接替（建议） | 缺少参赛方时暂停；有人明确接替空位后恢复原局 | 能继续原棋局，需要处理接替及断线保留期 |
| B：结束这一局 | 新房主和剩余成员组织下一局；不凭退出事件自动计算胜负 | 规则较简单，但原棋局不能接着玩 |

若选 A：主动退出立即释放原席位；意外断线先保留席位到宽限结束。在空位释放前不能让另一人占用；补位后建议现有参赛者确认准备，再从同一棋局恢复。不得将新加入者未确认地分配到一盘已经进行的棋局，或让本地 AI 自动接管。

观战、满房加入及主动接替的页面行为随该决定一起明确；现有代码已有观战连接能力，设计不能把它误报为本轮新实现。

## 7. 在线名单与自动清理

### 在线玩家的含义（待确认）

建议只显示已进入联网大厅或房间的玩家，包含自己；不把仍在玩本地游戏的网站访问者列入。这个名单应来自有效的联网会话，不使用匿名访问统计或历史昵称缓存推算。

同一浏览器多标签页的重复连接不能直接计成多个人；断线重连也不应生成重复名单。建议按现有联网身份去重，不按昵称合并，也不承诺识别不同浏览器中的同一个人。名单可以有短暂更新延迟，成员是否仍占据房间席位由房间服务的实际状态决定。

昵称和在线人数的采集／显示范围由这项决定控制。已有房间内的连接通知不足以显示“在大厅但尚未进房间”的人，后续需要额外的大厅在线会话记录。

### 房间清理标准（待确认）

| 规则 | 后果 | 现状／建议 |
| --- | --- | --- |
| 所有连接都离开后 5 分钟删除 | 有玩家或观战者连接就保留；思考多久都不触发删除 | 当前源码已有；建议沿用 |
| 没有参赛玩家 5 分钟删除 | 只有观战者的房间也会清理 | 需要额外区分观战连接并告知房间即将关闭 |
| 一定时间没有操作即删除 | 仍在线思考的玩家也可能被清理 | 时长与有效操作定义须再决定，不能直接使用落子时间或鼠标移动 |

清理必须由服务端计时；最后一个人的浏览器已经关闭时，前端定时器无法承担删除。清理时再次检查条件：计时期间有人有效回到房间，应取消或重新计算期限；删除房间状态与移出大厅列表须保持一致，失败有重试路径。

房主断线宽限、在线名单过期和房间删除是不同的计时用途，分别命名和测试。若服务器只有一个闹钟入口，应统一安排最近到期的事项，不能让一个计时覆盖另一个。

## 8. 技术边界与本地存档保护

### 在现有结构上增加能力

- **玩家页面**：大厅、建房选择、房间等待页和清晰的返回关系；继续复用准备页及原棋盘渲染。
- **房间服务**：增加房主、稳定加入顺序、成员连接状态、席位状态及需要的时间点；由房间统一判断准备、移交和接替权限。
- **大厅记录／现有房间索引**：提供有限的列表摘要和在线名单。加入、离开、昵称、准备、开始、结束、移交等事件更新摘要；不要要求每个大厅客户端逐个下载所有房间的完整棋局。
- **已有消息协议**：保留棋局同步、操作版本及撤销／重做协商；大厅新增字段与旧房间的兼容规则一起设计。旧数据没有房主时须给出稳定的补齐规则，不能直接清空旧房间。

字段名和接口划分由实施时决定。此处不是要求新增账号系统或更换后端；继续基于仓库已有服务评估。房主权限由服务端核对当前成员身份，不能仅通过前端隐藏按钮或昵称相等来判断。

### 进出联网不改变本地三档

1. 进入联网前保存正在玩的本地棋局，记住其实际所属档；未选本地档也可以打开大厅。
2. 建房预览、网络棋局、房间销毁和在线胜负都不写回本地三档，不增加推箱子完成记录。
3. 加入房间先完成读取和校验，再切换当前显示；取消、失败或迟到响应不得替换已返回的本地画面。
4. 离开房间先停止联网操作和清空房间归属，再恢复此前本地会话或停留在大厅；不能让在线快照被本地自动保存计时器写入旧档。
5. 房间里的显示偏好继续使用本地显示设置；房主不能通过移交或改名覆盖其他人的个人设置。

只浏览大厅不等于退出当前本地存档。在线页面的返回与 R18 的完整菜单整理保持边界，本轮不修改“设置 → Menu → Main menu”的全部结构。
