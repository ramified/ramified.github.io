# R19：联网大厅与房间流程设计

更新日期：2026-10-12。工作分支：`ramified_menu`。

**状态：设计草案，未实现。** 用户本轮明确要求先写设计文档。本稿只修改 Markdown；没有改动玩家页面、联网服务、翻译、存档或部署配置。下文分别标明用户要求、代码现状、建议与待确认项，建议不能当作已确认需求实施。

## 1. 用户已明确的目标

1. 有一个显示所有在线玩家和房间的界面，不采用此前仅列出大厅／房间玩家的建议。
2. 每个房间显示房间内玩家及游戏类型。
3. 创建房间时，房主先从游戏列表选择游戏并初始化；列表不包含推箱子这样的单人游戏。
4. 房主退出后，由剩余在线参赛成员中最早成功加入房间的人接任；不按棋子颜色、昵称或客户端显示顺序决定。
5. 所有棋手退出后结束本局；还有棋手留下时保留棋局，等待其他人接替空位。
6. 沿用“无人连接 5 分钟后删除房间”：既没有参赛玩家，也没有观战者时才计时。
7. 房主可以在原房间准备新的棋盘／游戏，确定内容后询问其他参赛玩家是否同意；不同意的参赛玩家退出房间，同意者留下使用新配置。观战者不需要表决，可留下或自行退出。
8. 房主可选择不限时，或设置三种时间限制：双方各自总时长、每步时长、总时长加 3 次读秒；具体时长由房主决定。
9. 读秒采用按周期消耗的规则：周期内落子不扣次数，耗尽一个周期才扣一次，最后一次耗尽则超时。
10. 棋手退出或断线后仍继续计时，缺席方也可能超时；不因为等待补位／重连暂停棋钟。

以上为 2026-10-12 的最新决定，替代草案中“限制在线名单范围”“创建后固定房间配置”和离席后两种方案任选其一的建议。多人超时结果、未回应配置请求等细节仍待确认。全部内容仍在设计阶段。

## 3. 先分清四种事情

这是本次设计的核心，页面只是这些规则的呈现。

| 概念 | 负责什么 | 例子 |
| --- | --- | --- |
| 大厅 | 发现在线玩家和可进入的房间 | 能看到某个五子棋房间正在等人 |
| 房间 | 聚集一组成员，保存房间配置和当前棋局 | 一局结束后仍可在同一房间继续 |
| 房主 | 管理这间房，不自动拥有其他人的落子权 | 白方接任房主后仍然是白方 |
| 棋手位置／阵营 | 决定谁能操作哪一方 | 原黑方退出，黑方会缺人；把房主交给白方不能补上黑方 |

因此，“房主移交”“棋手退出”“房间删除”是三个不同事件，分别处理。昵称只是显示名，不用于判断谁有房主权限或属于哪个阵营。

## 4. 页面和进入路径（建议，待确认）

建议在主菜单增加独立的“在线游戏 / Online play”入口，直接进入大厅。联网无需先选择本地存档；原“开始游戏 → 选择存档”的本地流程保持原样。

```text
主菜单
  开始游戏 → 选择存档 → 本地游戏列表 → 原准备页／选关
  在线游戏 → 联网大厅
               ├─ 创建房间 → 多人游戏列表 → 联网准备页 → 创建 → 房间等待页
               └─ 选择已有房间／输入房间码 → 加入 → 房间等待页或当前棋局
  设置

房间等待页 → 满足开局条件 → 当前对局 → 结束／再来一局
退出房间 → 联网大厅 → 主菜单
```

本稿将用户所说的“窗口”理解为**游戏框内的完整大厅页面**，沿用固定 4:3 外框、黑底白字标题、全屏和内部滚动，不添加居中小弹窗或新的卡片风格。具体入口位置仍列为待确认项，不借此重排 R18 的所有设置按钮。

### 大厅只展示必要信息

| 区域 | 内容 | 行为 |
| --- | --- | --- |
| 自己 | 沿用现有昵称设置 | 不额外增加注册流程 |
| 在线玩家 | 所有在线玩家的昵称和人数，包含本地玩家；运行口径见第 7 节 | 显示事实，不把访问统计当作在线名单 |
| 房间列表 | 房间码、游戏类型、房间成员、房主标记、参赛人数／席位及等待／进行中等状态；加入前可查看时间设置 | 加入资格由实际房间再次检查，列表可能短暂过期 |
| 操作 | 创建房间、原房间码加入、返回 | 保留房间码作为直接进入的办法 |

建议房间按行展示，成员昵称在同一行的附属文字中，不为每个玩家加一张卡片。多人列表过长可在内容区域滚动；全屏内容居中，窄屏区域上下排列。布局尺寸在之后的实现中检查，本轮不生成新的美术草图。

空列表、正在连接、获取失败必须是不同状态。获取失败不能显示成“当前没有玩家／房间”；保留重试和返回。

### 返回和退出不能混为一谈

- 建房游戏列表返回大厅；准备页返回该列表，“更多”返回准备页并保留本次修改。
- 按下最终创建之前不产生服务器房间；取消不会留下空房间。
- 房间内打开设置、返回棋盘，不表示离开房间，也不移交房主。
- 建议“退出房间”是明确操作，成功后返回大厅。房间未退出时不允许悄悄加入第二个房间。
- 刷新、关闭标签页、网络中断按断线处理，不能假定浏览器一定能送达主动退出消息。

## 5. 创建房间与游戏范围

### 保留现有支持范围

| 游戏 | 建房列表 | 联网准备要求 |
| --- | --- | --- |
| Hex | 包含 | 沿用现有棋盘和交换规则选项，两个阵营由联网玩家控制 |
| 五子棋 | 包含 | 沿用现有棋盘准备布局，移除本地 AI 控制者选项 |
| 围棋 | 包含 | 沿用棋盘、贴目等原选项 |
| 四子棋 | 包含 | 沿用棋盘与下落方向，不带入本地 AI |
| 黑白棋 | 包含 | 沿用棋盘选项 |
| 中国跳棋 | 包含 | 可用阵营随棋盘确定；同一人是否仍可控制多个阵营需确认 |
| 国际象棋 | 仅对局 | 按目录 `fideChessVariant` 过滤；不显示皇后等单人谜题 |
| 台球 | 仅双人模式 | 保留棋盘和原摆球流程，建房使用已确认的初始摆球 |
| 推箱子、2048、连连看 | 不包含 | 本轮不扩展其玩法或加入联机支持 |

复用原 2×3 游戏图片分页，按现有游戏顺序过滤，避免另维护一份图片或排序。国际象棋对局／谜题、台球单人／双人须按实际模式判断，不能只按游戏名称过滤；前端与服务端都要检查。

### 建房准备的建议规则

1. 新进入准备页使用现有玩家入口的棋盘／参数默认值；联网覆盖仅包括关闭本地 AI、台球固定双人、国际象棋固定对局。
2. 保留预览两侧切换、预览下方必要选项、左下更多、右下提交按钮；最终按钮为“创建房间”，不先偷偷开始一局本地游戏。
3. 两人游戏的“人类／AI”区域改为联网席位信息。建议创建者可选自己的阵营，其余空位显示等待玩家；默认第一阵营，其他加入者选择空位。跳棋的多阵营分配单独确认。
4. 本次准备内切换棋盘／更多再返回仍保留草稿。随机棋盘、拓扑和台球摆球只在准备中确定，创建时使用相同结果，不重新生成。
5. 创建后进入等待页，不立即允许落子。服务器保存唯一的初始棋局，其他成员加入时获取同一版本。
6. 创建请求成功但应答丢失时，重试应找到同一次创建的房间，避免连续生成重复房间；只完成创建、未成功连接的房间由空房间规则清理。

### 房间内改棋盘／换游戏（已确认允许，同意流程细节待确认）

用户已明确：房主先确定新的游戏内容，再征询房间内其他参赛玩家的意见；观战者不表决。因此撤销此前“首版创建后固定配置”的建议。

建议流程：

```text
房主选择更改 → 在准备页确定新游戏／棋盘／参数
             → 提交完整配置提案 → 其他参赛玩家查看并回应
             → 拒绝者退出，同意者留下；未回应者按另定规则处理
             → 留下的参赛玩家均明确同意后应用新配置 → 重新分配席位并准备 → 新局
```

- 房主浏览或编辑的是草稿，提交前不覆盖原棋局，不把未确定的每次修改都弹给其他人。取消草稿返回原房间。
- 提案显示将改成的游戏、棋盘、重要规则及时间限制，并说明应用后会开始新局。建议修改棋钟也走同样流程，避免中途单方面减少他人的时间。
- **用户已明确：不同意的玩家退出房间，同意的人留下使用新配置。** 征询按钮应清楚表达“同意新配置”与“不同意并退出房间”，避免把关闭界面或取消浏览当作拒绝。
- **观战者不参与同意条件，允许留在房间或自行退出。** 未回应、断线的参赛者，以及提案期间新加入参赛的人如何处理仍待确认。未点击同意不能自动视为同意，也不能自行规定超时踢出。
- 同意针对同一份配置版本；房主再次修改内容后，旧的同意不覆盖新版本。服务端只应用一次已满足同意条件的提案；验证／加载失败不先清除旧局。
- 新游戏可能改变人数和阵营，例如跳棋改五子棋。建议重新选空位，未获得席位者保留为观战者；不能把同意更改理解为保证原席位不变。此规则需确认。
- 提案期间当前对局和棋钟是否暂停、房主中途退出后是否撤销提案、是否允许在对局进行中发起更改，列入后续待决定项。不得用反复编辑草稿自动暂停他人的棋钟。
- 应用新配置后清除旧的准备状态，重新确认开局；原局与新局使用不同对局编号，迟到的落子或同意消息不得作用于新局。

## 6. 等待、开局与成员离席

### 等待页与开局（建议）

等待页显示游戏／棋盘名称、成员、阵营、房主和准备状态。参与者自行准备或取消准备；观战者没有落子权，也不阻碍参赛者完成准备。

首版建议保留现有“参与者均准备后开局”的方式，同时补齐两个条件：

- 双人游戏必须有两位不同的在线玩家，所需双方均有人控制。
- 跳棋至少两位不同的在线玩家，启用的全部阵营均有控制者；一人多阵营是否保留仍待确认。

若希望“所有人准备后，再由房主点击开始”，需明确选择该方案；不能同时把自动开局和房主手动开局写成要求。游戏开始后保留原棋盘和操作，不把房间成员列表一直盖在棋盘上。

### 房主移交（顺序已确认，断线边界待确认）

用户已确认“第二位”定义为**剩余在线参赛成员中，最早成功加入房间的人**，不按棋子颜色、昵称排序或各客户端画面顺序判断。建议在宽限内断线重连保留原加入顺序；主动离开后再进房间算新加入，这条重连细则仍待确认。

| 场景 | 处理规则及确认状态 |
| --- | --- |
| 房主明确退出房间 | 立即选出继任者并通知全体；保留房间码和当前棋局 |
| 同时有多人离开 | 服务端完成成员变更后选择一次有效继任者，不能出现两个房主 |
| 只是短时断线／刷新 | 建议保留 60 秒重连机会；到期仍未连接才移交。60 秒为建议值，不是用户已确认值 |
| 旧房主在移交后重连 | 作为普通成员返回，不自动夺回房主；原席位是否保留按断线／接替规则处理 |
| 新房主继续退出 | 按相同加入顺序继续移交 |
| 只剩观战者 | 没有符合已确认定义的继任候选，不能自动让观战者接任；如何在之后有人申请参赛时恢复房主仍待决定 |
| 无任何成员 | 暂无房主，进入空房间宽限；若允许在期限内重新加入，建议首位有效参赛者接任 |

移交由服务器决定并保存，不依靠房主浏览器先发出“指定继任者”的消息。因此关闭浏览器也有可执行的后续流程。转移的是管理权，不修改棋盘、轮到谁、阵营归属或已完成操作。

### 棋手离席（2026-10-12 已确认）

这里对普通棋手和房主使用同一条规则，房主另外发生管理权移交。

| 事件 | 本局如何处理 | 房间如何处理 |
| --- | --- | --- |
| 部分棋手退出，至少还有一位棋手留下 | 保留棋局，等待有人接替空位；按当前回合继续计时，缺席方可能超时 | 保留；若退出者是房主则按确认的顺序移交 |
| 所有棋手退出，仍有观战者 | 结束本局；不再把它作为等待补位的进行中棋局 | 保留，尚不启动 5 分钟删除计时 |
| 所有棋手和观战者都退出 | 结束本局 | 从最后一个连接离开时起，5 分钟后仍无人连接则删除 |
| 只是断线，尚在重连宽限期内 | 不立刻视为主动退出；是否及何时转为正式离席待确认 | 连接为零时可同时开始现有空房间计时；有效重连取消删除 |

“所有棋手”指本局参与者，不包括观战者；建议按当前席位参与关系判断。一局因全部退出而结束后，后来有人加入不能把旧局悄悄复活。此类结束建议记为未分胜负的中止，不自动给观战者或最后离开的人算赢，具体结果展示待确认。

主动退出释放席位；意外断线建议先保留到重连宽限结束。在空位释放前不能让另一人占用。新加入者需明确选择接替，不能自动开始操作残局。计时局建议接替者继承该席位的剩余时间和读秒次数，避免借换人重置棋钟；细则待确认。

为使“继续计时”与可操作性一致，离席不应把仍在线的棋手锁在无法行动但继续扣时的界面。正常回合中，在线方在自己的回合仍可完成合法行动；轮到缺席方时保留该回合并继续扣其时间，直到接替、重连或超时。此前“补位后要求全体重新准备再恢复”的建议撤销，补位不能借此暂停原局；新局仍按正常准备流程启动。多人跳棋的并行开局计时另待定义。

现有代码已有观战连接能力。所有棋手退出后只剩观战者的房间可能持续存在，这是用户确认的“无人连接才删除”规则的直接结果，不额外增加观战超时删除。

## 7. 在线名单与自动清理

### 在线玩家的含义（已确认显示所有玩家）

用户已选择“所有玩家”，撤销此前只统计大厅／房间玩家的建议。本稿将任务范围内的“所有玩家”落实为：**打开这个游戏集且在线状态仍有效的人，包括主菜单、本地游戏、联网大厅、房间参赛者和观战者，也包括自己。** 不要求先点击在线游戏。若还要涵盖网站中与游戏集无关的其他页面，需要另明确页面范围，不能从本需求扩展为全站访客展示。

这是对“所有玩家”的运行口径说明。页面开着但已断网不能永久算在线；名单以会话连接／存活信号为依据，不使用匿名访问统计或历史昵称缓存推算。在线状态失效的宽限与后台标签页策略仍需在实施前确定。

同一浏览器多标签页的重复连接不能直接计成多个人；断线重连也不应生成重复名单。建议按现有联网身份去重，不按昵称合并，也不承诺识别不同浏览器中的同一个人。名单可以有短暂更新延迟，成员是否仍占据房间席位由房间服务的实际状态决定。

已有房间内的连接通知无法覆盖本地游戏和主菜单中的玩家，需要游戏集页面级的在线会话记录。建议未设置昵称时沿用现有自动昵称，不为所有本地玩家增加一道必填命名页面。大名单的分页／内部滚动不得悄悄遗漏玩家；不另加聊天、邀请或社交信息。

### 房间清理标准（已确认沿用 5 分钟）

| 状态 | 是否进入房间删除计时 | 本局状态 |
| --- | --- | --- |
| 至少一名参赛者或观战者连接 | 否 | 按正常对局／离席规则处理 |
| 无参赛者、无观战者连接 | 是，连续 5 分钟 | 主动退出导致全部棋手离席时已结束本局；意外断线按宽限规则另处理 |
| 到期前有人有效连接回来 | 取消本次删除计时 | 已正式结束的局不因重连自动恢复为进行中 |
| 连续 5 分钟仍无任何有效成员连接 | 删除房间并移出列表 | 不影响本地三档 |

这里统计的是**该房间的有效成员连接**。仅在大厅看房间列表、其他房间有玩家或本地玩家在线，不会让这间空房持续存活；未完成加入的请求也不能当作参赛者或观战者。已经有连接但长时间未落子不触发房间删除；对局时限由棋钟单独处理。

清理必须由服务端计时；最后一个人的浏览器已经关闭时，前端定时器无法承担删除。清理时再次检查条件：计时期间有人有效回到房间，应取消或重新计算期限；删除房间状态与移出大厅列表须保持一致，失败有重试路径。

## 8. 房主设置时间限制（模式和读秒已确认，未实现）

### 三种模式和可配置参数

用户已确认保留不限时及以下三种计时模式，时长由房主决定。表中的数字只用于解释，不是擅自确定的默认值。

| 模式 | 房主设定什么 | 运行方式 |
| --- | --- | --- |
| 不限时 | 不需要时长参数 | 不启用对局棋钟，房间删除规则仍适用 |
| 各自总时长 | 每方的初始总时间，例如各 10 分钟 | 轮到自己时累计扣自己的时间，换对方行棋时停止；是否支持双方不同初始时长待确认 |
| 每步时长 | 每步可用时间，例如 30 秒 | 每次轮到该方时开始一段新的时间；本步没用完的秒数不累计到下一步 |
| 总时长＋3 次读秒 | 每方总时间、每个读秒周期时长，读秒次数固定为 3 | 总时间耗尽后进入读秒；次数按下方已确认规则消耗 |

初始默认模式及数值上下限仍待确认。建议将时间设置放入联网准备页的“更多”；等待页和加入房间前显示简短的已选规则。实际对局显示当前方剩余时间／读秒次数，具体位置后续沿用现有 UI 评估；不添加语音、音效或动画设计。

### 读秒的解释与例子（已确认）

用户已确认采用按周期消耗的日式读秒：进入读秒后，按时完成一步会重置当前周期的秒数，保留剩余次数；完整耗尽一个周期才减少一次；最后一个周期耗尽时构成超时。围棋的读秒包含这种可重复使用的周期概念，英国围棋协会的说明提供了相应例子；这里将其写为适合本游戏集的数字周期方案，而非要求照搬职业比赛计时细节。[BGA：Byoyomi Explained](https://www.britgo.org/bgj/10643.html)

例如“总时间 10 分钟＋3×30 秒”，**在总时间已用完、还剩 3 次读秒的前提下**：

| 本步实际用时 | 本步结束后 | 下次轮到自己时 |
| --- | --- | --- |
| 20 秒 | 仍有 3 次读秒 | 当前周期重新从 30 秒开始 |
| 40 秒 | 消耗 1 次，剩 2 次 | 当前周期重新从 30 秒开始，已用掉的次数不恢复 |
| 70 秒 | 消耗 2 次，剩 1 次 | 当前周期重新从 30 秒开始 |
| 90 秒仍未完成合法一步 | 最后一次也耗尽，触发超时 | 如何结束／裁定本局由下节规则决定 |

示例各行都是从“剩 3 次”独立开始。3 次包含当前正在倒数的周期，不是 3 次之外再送一次；最后 1 次只要每步及时完成就可继续使用，并非总共只能再走 3 步。若总时间在本步途中归零，只将之后经过的时间计入读秒。精确到期瞬间的判定应由服务端统一处理，不依赖浏览器显示四舍五入后的秒数。

该模式及上述周期语义已确认。超时后的对局结果、停钟条件等按下文另行确定。

### 超时与各游戏的关系（需要决定）

棋钟记录“谁在何时用尽时间”，对局规则决定结果。标准国际象棋通常超时判负，但若对方不可能通过任何合法走法将死则判和；本游戏集还有变体棋盘和多人游戏，因此不能仅写一句“所有游戏超时统一判负”就视为规则齐全。[FIDE Laws of Chess，第 6.9 条](https://handbook.fide.com/chapter/E012023)

- 双人游戏：建议超时结束本局，并按该游戏规则确定结果；国际象棋标准对局的判和例外和变体棋盘如何处理须明确。
- 多人跳棋：某一方超时后是整局结束、该方退出还是等待接替，尚未决定；不能新增自动淘汰棋子或 AI 接管规则。
- “每步”应指服务器接受的一次完整合法行动，不是一次点击。跳棋连续跳跃、国际象棋升变、Hex 交换、围棋停着，以及台球放置母球／击球等，需要逐项定义完成时点。
- 跳棋开局可能允许多方操作，一人也可能控制多个阵营；计时按人共享还是按阵营独立、此阶段是否并行计时均待确认。
- 台球的选角度与力度、击球后模拟动画，围棋终局数子／确认等阶段，需要明确计时边界。建议只计玩家能作出决定的时间，具体规则不能靠前端动画长短决定。

### 与房间流程衔接

| 情况 | 建议／必须保持的边界 | 状态 |
| --- | --- | --- |
| 房间等待或准备棋盘 | 正式开局前不启动棋钟 | 建议 |
| 房主移交、改昵称、刷新 | 不重置各方剩余时间和读秒次数 | 计时正确性要求 |
| 对局超时结束 | 停止本局棋钟；不等于房间为空，不启动 5 分钟删除，也不自动踢出超时玩家 | 生命周期区分 |
| 部分棋手退出等待补位 | 棋局保留，继续按当前回合扣时，缺席方也可能超时；未轮到的方不同时扣时 | 已确认继续计时 |
| 短时断线 | 同样继续计时，不因刷新或重连重置；房主／席位重连宽限不额外赠送思考时间 | 已确认不停钟；身份／席位宽限时长仍待定 |
| 有人接替空位 | 建议继承该席位的剩余时间／读秒次数；不重新发放开局时间 | 建议，待确认 |
| 所有棋手已正式退出 | 结束本局并停止棋钟；观战者仍可使房间保留 | 由已确认的离席规则推导 |
| 同意并应用新游戏／棋盘／计时提案 | 建议新局在重新准备并开局后使用新初始时间；提案草稿和未完成征询不重置旧棋钟 | 建议，待确认 |
| 撤销／重做 | 是否恢复历史用时须明确；建议默认不返还已经消耗的思考时间 | 建议，待确认 |

棋钟由服务端时间及已保存状态计算，浏览器负责显示；切换标签页、前端卡顿或房主关闭浏览器不应使棋钟停止。服务需保存计时模式、时长、各方剩余量、当前计时阶段及对局版本；不依靠每秒向存储写一次或某个浏览器的定时器判输。合法动作与到期事件同时到达时要使用同一时间边界处理，只结算一次。

房主断线宽限、在线名单过期、房间删除及棋钟到期是不同的计时用途，分别命名和测试。若服务器只有一个闹钟入口，应统一安排最近到期的事项，不能让房间清理计时覆盖棋钟或断线处理。

## 9. 技术边界与本地存档保护

### 在现有结构上增加能力

- **玩家页面**：大厅、建房选择、房间等待页、配置征询和棋钟显示，提供清晰的返回关系；继续复用准备页及原棋盘渲染。
- **房间服务**：增加房主、稳定加入顺序、成员／席位状态、配置提案和棋钟；由房间统一判断准备、移交、接替及配置生效条件。
- **在线会话与房间索引**：覆盖所有游戏集页面中的玩家；房间只发布必要摘要。加入、离开、昵称、准备、开始、结束、移交及配置生效等事件更新列表；不逐个下载所有房间的完整棋局。
- **已有消息协议**：保留棋局同步、操作版本及撤销／重做协商；新增字段与旧房间的兼容规则一起设计。旧房间无房主或棋钟配置时须定义兼容行为，不能清空旧房间或未经成员确认强加时限。

字段名和接口划分由实施时决定。此处不是要求新增账号系统或更换后端；继续基于仓库已有服务评估。房主权限由服务端核对当前成员身份，不能仅通过前端隐藏按钮或昵称相等来判断。

### 进出联网不改变本地三档

1. 进入联网前保存正在玩的本地棋局，记住其实际所属档；未选本地档也可以打开大厅。
2. 建房预览、网络棋局、房间销毁和在线胜负都不写回本地三档，不增加推箱子完成记录。
3. 加入房间先完成读取和校验，再切换当前显示；取消、失败或迟到响应不得替换已返回的本地画面。
4. 离开房间先停止联网操作和清空房间归属，再恢复此前本地会话或停留在大厅；不能让在线快照被本地自动保存计时器写入旧档。
5. 房间里的显示偏好继续使用本地显示设置；房主不能通过移交或改名覆盖其他人的个人设置。

只浏览大厅不等于退出当前本地存档。在线页面的返回与 R18 的完整菜单整理保持边界，本轮不修改“设置 → Menu → Main menu”的全部结构。
