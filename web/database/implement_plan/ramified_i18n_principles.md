# Long-Term i18n Principles for Ramified Minigames

## Goal

Prevent newly added games or UI controls from silently falling back to English.

## Core rule

Use **explicit translation keys for all new UI text**.

Do not rely on automatic English-source matching except as a compatibility layer for existing/legacy code.

## Translation strategy

### 1. Static HTML

Every visible static label, button, option, help text, placeholder, or accessibility string should use an explicit `data-i18n` key.

```html
<span data-i18n="setup.hexPieRule">Pie rule</span>
<button data-i18n="setup.hexSwapColors">swap colors</button>
```

If the translated text is next to an `<input>`, wrap only the text in a child `<span>` rather than putting `data-i18n` on the parent `<label>`.

### 2. Dynamic JavaScript — fixed text

For text generated by JavaScript, use a stable locale key rather than depending on exact English matching.

Preferred pattern:

```js
tk(
  'setup.hexRules',
  'Red and blue alternately fill tiles...'
)
```

All games should follow the same convention.

### 3. Dynamic JavaScript — variable sentences

Do not build translatable sentences by concatenating English fragments.

Avoid:

```js
`${playerLabel}; may swap colors`
```

Prefer a parameterized locale entry:

```js
tk(
  'runtime.hexPieAvailable',
  '{{player}}; may swap colors',
  { player: playerLabel }
)
```

Locale entry:

```js
'runtime.hexPieAvailable': [
  '{{player}}; may swap colors',
  '{{player}}；可以交换颜色'
],
```

This lets each language control word order and punctuation.

### 4. `tr()`, `__patterns`, and `__fragments`

Keep these for backward compatibility only.

Do not use them as the primary strategy for newly added UI.

In particular, avoid adding new generic English fragments when a dedicated translation key would be clearer.

## Required checks for every new game

A new game is not complete until it has:

- a translated game name
- translated quick rules
- translated setup controls
- translated runtime/status messages
- translated buttons and menu options
- translated accessibility text where applicable

## Missing-translation detection

Add a development-only warning when Chinese is active and a translatable English string remains unchanged.

Example:

```js
function warnIfUntranslated(source, translated) {
  if (
    window.SiteI18n?.getLocale?.() === 'zh-CN' &&
    source === translated &&
    /[A-Za-z]{2,}/.test(source)
  ) {
    console.warn('[i18n] Possibly untranslated:', source);
  }
}
```

Integrate this into the translation path used by dynamic UI.

This should be a warning, not a hard error, because some names may intentionally remain in English.

## Recommended Codex implementation work

1. Audit `ramified_minigames.html` for visible English without `data-i18n`.
2. Audit JavaScript for user-visible strings created dynamically.
3. Add stable translation keys for new/dynamic strings.
4. Replace sentence concatenation with parameterized translation entries.
5. Keep current English-source matching as a legacy fallback.
6. Add development-only missing-translation warnings.
7. Add a lightweight test or validation script that checks required translation keys for every registered game.
8. Document that future games must use explicit keys before merge.

## Desired end state

The locale system should behave like this:

```text
Static HTML
    -> data-i18n key

Dynamic fixed text
    -> explicit locale key

Dynamic text with variables
    -> parameterized locale key

English-source matching / fragments / regex
    -> legacy fallback only
```

The main objective is that adding a new game without translations should produce an obvious development warning instead of silently showing English in production.
